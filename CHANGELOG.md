# Sentora-2027 for Ubuntu 26.04 — Change Log

Released 2026-11-05

## Overview

Sentora-2027 is this build of Sentora for Ubuntu 26.04 only (based on the upstream Sentora 2.0.2 with its master installers), on PHP 8.5, MySQL 8.4 and Apache 2.4, and rebuilds its security from the ground up. Every hosted account now runs as its own Linux user, the panel runs as its own user, and every module was checked for cross-account access, injection and script-injection flaws.

It is delivered as GitHub releases of [sentora-core-2027](https://github.com/RusTus/sentora-core-2027/releases) (the core zip) and [sentora-installers-2027](https://github.com/RusTus/sentora-installers-2027/releases) (the other files), both with the same tag:

| File | What it is |
| --- | --- |
| `sentora2027-ub26.04` | The installer (Ubuntu 26.04 only) |
| `sentora-core-2027.zip` | The panel: core, modules, bundled apps (phpMyAdmin, Roundcube, Matomo and others) |
| `sentora-installers-2027.zip` | Service configs, SQL, build sources (zsudo, GoAccess), fail2ban, SOGo templates |
| `sentora-php-8.2-ubuntu26.04-amd64.tar.gz` to `sentora-php-8.4-…` | Extra PHP versions built for 26.04 (three files) |

A fresh install is required: folder ownership, users and Apache's setup are created by the installer and cannot be converted from an older server.

## Platform and installer

The installer targets Ubuntu 26.04 only and refuses any other system. Everything comes from Ubuntu's own packages except the parts Ubuntu does not ship, which are bundled or built from source.

| Component | Original | Now |
| --- | --- | --- |
| Operating system | Ubuntu 16.04 to 22.04, CentOS, Debian | Ubuntu 26.04 only |
| PHP | 7.x through mod_php | 8.5 (Ubuntu) through PHP-FPM; extra versions 8.2 to 8.4 per domain |
| Database | MySQL 5.x or MariaDB | MySQL 8.4 |
| Web server | Apache 2.4, prefork engine, mod_php | Apache 2.4.66, event engine, HTTP/2, no mod_php |
| Mail | Postfix, Dovecot 2.2 | Postfix 3.10, Dovecot 2.4, SOGo 5.12 |
| DNS | BIND 9 | BIND 9.20 |
| FTP | ProFTPD, plain FTP | ProFTPD 1.3.9 with FTPS required |

**Installer behaviour**

- Downloads the core and installer zips and PHP bundles from the GitHub releases (the release tagged `current`, set by `SENTORA_RELEASE_TAG`; a new version replaces that release's files), with three retries, archive checks and a check against the SHA-256 GitHub lists for each file; `SENTORA_DOWNLOAD_URL` downloads from your own web server instead.
- Waits up to 30 minutes for Ubuntu's automatic updates to release the package lock, instead of failing.
- Checks the clock against Ubuntu's archive (or GitHub) and stops, with the command to fix it, when it is off by more than 2 minutes (apt rejects package lists from a clock that is behind).
- Stops with a clear message if the compiler or other build tools did not install.
- Checks that every package it installs really installed; if not, reads the package lists again and retries up to 3 times a minute apart (Ubuntu's mirrors can briefly list a package that was just replaced), then shows a clear error naming any that still did not install.
- Detects the public IP from four services and validates it, falling back to the local IP.
- Creates a self-signed TLS certificate (RSA 3072, 10 years) used by the panel, mail and FTP until Let's Encrypt replaces it.
- Writes every generated password to `/root/passwords.txt` (mode 600).
- Passes `shellcheck` with no warnings.

## Security architecture

In the original, the panel and every hosted site ran PHP as the same user (`www-data`), the panel folder was world-writable, and a setuid helper ran any command as root, so any site could take over the server. Each layer below closes part of that.

| Layer | Original | Now |
| --- | --- | --- |
| Panel | Ran as `www-data` with every site | Own user `sentora`, own PHP-FPM pool; sessions and uploads in `/var/lib/sentora` (private) |
| Hosted accounts | All sites as `www-data` | Each account as its own user `web<id>`, own PHP-FPM pool per PHP version it uses |
| Account folders | World-readable and writable | Owned by the account; access lists give the panel read-write and Apache read-only, nobody else anything |
| Temp and sessions | Shared `/var/sentora/temp` | Each account's own `tmp` folder |
| Panel code and configs | `chmod -R 777` | Owned by root, nothing writable by anyone else |
| Secrets | `cnf/db.php` readable by every site | Database password, encryption key, webmail and phpMyAdmin configs readable by root and the panel only |
| zsudo | Ran any command as root, for anyone | Fixed list of reloads, executable by root and the panel only |
| Module installs | Panel user wrote module code the root daemon ran | Queued by the panel, made by the root daemon after re-checking |
| FTP and cron | Ran as `www-data` | Run as the account's own user |

**Login and browser protection**

- Login lockout: 5 wrong passwords for an account, or 20 from one address, within 15 minutes locks logins for 15 minutes.
- "Remember me" is a random token stored hashed and replaced on each use (it used to store the password hash in a cookie).
- Optional two-factor login (6-digit authenticator codes), switched on in Sentora Config and set up per account in My Account.
- Session cookies are `HttpOnly`, `SameSite=Lax` and `Secure` on HTTPS; session ids are refused unless the server made them, and renewed at login.
- Password-reset keys, CSRF tokens and salts come from a cryptographic random generator; reset keys work once, for one hour.
- A content security policy, frame protection and `nosniff` on every panel page.

**Server-wide**

- fail2ban blocks an address for an hour after 5 failures in 10 minutes on SSH, SMTP login, IMAP/POP3, webmail, SOGo, FTP, phpMyAdmin and the panel (custom filters for Dovecot 2.4, ProFTPD and the panel).
- The logs fail2ban acts on cannot be written by hosted sites, so a forged line cannot get an address blocked.

## Security fixes in the original code

Each fix below was reproduced as an attack on the test system before the change and refused after it.

| Area | Flaw | Severity | Fix |
| --- | --- | --- | --- |
| zsudo | Any local user or site could run any command as root | Critical | Fixed allowlist of reloads; root and panel only |
| Panel files | World-writable panel code run by the root daemon | Critical | Root-owned code; panel as its own user |
| Domains, subdomains, parked domains, databases, MySQL users, mailboxes, aliases, distribution lists | Any account could delete or change another account's items by sending its id | High | Shared ownership check before every action (14 actions, 9 modules) |
| Edit pages | `?other=<id>` showed another account's details | Medium | Loaders return only the account's own records |
| DNS Manager | Records could be added to or viewed on another account's domain | High | Domain ownership checked on display, save and default records |
| Manage Clients, Packages | A reseller could create administrators, and edit or delete other resellers' clients and packages | High | Only offered groups (no Administrators for non-admins), own clients and packages only |
| Backups | Full site and database backups built in the web folder with guessable names and left there; MySQL root password on the command line | High | Private work folder, random names, password in a 0600 option file, strict login checks |
| Cron Manager | Timing field wrote any line into the crontab; owner taken from the form; `../` paths | High | Validated timing and path, owner from the session, jobs run as the account |

| Several pages | Script injection through cron descriptions, FAQ text, group names, domain names, Domain Logs lines | Medium | Escaped output |
| Webalizer Stats | Reports in the web folder, readable by anyone who guessed the path | Medium | Reports outside the web root, owner-only viewer |
| Sentora Config, Apache Config, DNS Config | Settings the root daemon runs or uses as paths (zsudo, httpd_exe, apache_restart, zip_exe, hosted_dir, log_dir, ftp_php and others) were editable by any panel administrator, so an admin session could run any program as root | Critical | 29 such settings locked in the panel (changeable with `setso` as root only) |

| Several admin pages | No CSRF check on DNS Config, Module Admin, AutoIP, Sencrypt certificate actions and others | High | Every panel action must be a form post with the session's token, checked centrally; the token is added to every form automatically |
| Domains, Sub Domains, FTP | "Use an existing folder" accepted `../`, so a domain or FTP account could point at another account's files (Apache serves static files and source from any account) | High | Only folders inside the account's own folder |
| DNS Manager | Line breaks in TXT/SPF records were written into the zone file, adding any line (such as `$INCLUDE`) | Medium | Control characters removed when saved and again when zones are written |
| phpMyAdmin | Its `/setup/` page answered anyone | Medium | Removed from the bundle |
| Panel web folder | Page templates (`.ztml`, `.zpm`), `inc/`, `dryden/`, `cnf/` and daemon jobs could be requested or run directly | Low | Refused (403) |
| BIND | Zone transfers allowed to any address; version shown | Medium | Transfers only to the trusted servers; version hidden |
| Apache, Postfix | TRACE enabled, version in error pages; mail logins allowed below TLS 1.2 | Low | TRACE off, signature off, HSTS on the panel; TLS 1.2+ where TLS is required |
| Shared folders under `/var/sentora` | World-writable since install: a site could swap its log file for a link to a root-owned file (Apache writes logs as root) or rename folders root's jobs use | Critical | Root-owned; domain logs readable by root and the panel only; temp folders sticky; kept so by the daemon every run |
| Backups, Sencrypt download | `zip` followed symbolic links, so a link in a site could copy the panel's database password (or, for the daily root backup, any file) into the account's own backup | High | Links stored as links (`zip -y`) |
| Apache (hosted sites) | `FollowSymLinks` let one account serve another account's non-PHP files through a link | High | Only same-owner links (`SymLinksIfOwnerMatch`); `.htaccess` can not turn `FollowSymLinks` back on |
| Webalizer, Visitors | The log analysers ran as root while parsing text website visitors control, so a parsing bug in these older C programs would have given root | High | They run as `sentora-stats`, which can read nothing else; the root job opens the logs and passes them on standard input |
| Visitor Stats | Reports were world-readable, so any account's site could read every other account's traffic reports | Medium | Readable by root and the panel only |
| phpMyAdmin | Its login accepts MySQL root and nothing slowed down password guessing (no fail2ban jail) | High | Failed logins logged to a file only the panel can write; new `sentora-phpmyadmin` jail; the filter is anchored so a forged user name can not get another address banned |
| Panel working folders | `etc/tmp` and Matomo's `tmp` and `config` folders were readable by every site's user | Medium | Closed to the sites (panel and Apache only), kept so by the daemon |
| MySQL | Listening on this server only relied on the package's own setting, and the X protocol (port 33060) was not set | Low | `bind-address` and `mysqlx-bind-address` set to 127.0.0.1 explicitly |
| HTTPS (testssl.sh 3.2.5) | Panel pages were gzip-compressed while carrying CSRF tokens (BREACH); TLS 1.2 still offered CBC and plain-RSA ciphers (LUCKY13); two Cache-Control headers | Medium | PHP pages no longer compressed (images, CSS and scripts still are); Mozilla "intermediate" cipher set (forward secrecy, AES-GCM and ChaCha20 only); one Cache-Control header. testssl.sh rating A+ before and after; low findings 27 to 1 |
| Mail and FTP (testssl.sh on the live server) | Postfix offered anonymous ciphers (no certificate check) on ports 25, 465 and 587, and TLS 1.0 and 1.1 on port 25; Postfix, Dovecot and ProFTPD offered CBC and Camellia ciphers | High | All use the web server's modern cipher set (forward secrecy, AES-GCM and ChaCha20); TLS 1.2 or later everywhere, port 25 included; no anonymous ciphers. Checked with testssl.sh and direct connections |
| Mailboxes | Mailbox passwords were stored as unsalted MD5 ({PLAIN-MD5}), quick to crack from a copy of the database | High | New and changed passwords (panel and Roundcube) are {SHA512-CRYPT} hashes: salted SHA-512 crypt, 50,000 rounds. Dovecot (and Postfix SMTP logins through it) reads the scheme from the prefix; SOGo's mailbox view keeps the new prefix (updated by the daemon on existing servers). Existing mailboxes keep working and move to the new hash when their password next changes |
| Backup module (Advanced > Backup) | The download followed symbolic links: a client could put a link named like a backup in their own backups folder and download any file the panel can read, including the panel's database settings with the MySQL root password (proven on the test system); the daily purge, which runs as root, followed a link put in place of the backups folder and deleted old files wherever it pointed; the daily backup was written into such a link as root; the backup page had no CSRF check and no limit, so any website could make a logged-in client's browser fill the disk with backups | Critical | All backup file access goes through sys_backup: the backups folder must be a real folder, checked right before each use; only real files with a backup name are listed, served, deleted or purged; a download opens the file and checks it is the one checked (device and inode); new backups are renamed into place; the backup page checks the CSRF token and makes one backup at a time, at most one every 2 minutes |
| Hosted sites' .htaccess | A site's own .htaccess could hand its PHP files to the panel's PHP-FPM pool (SetHandler "proxy:unix:/run/php/sentora-panel.sock|...", or RewriteRule [H=...]) and run them as the panel's user, with access to every account, the panel's sessions and its database settings; any request reaching a pool that is not the account's own also left that site's PHP settings in the worker (PHP-FPM keeps settings sent with a request), which broke the panel for everyone and could plant settings in another account's pool; and a site could publish the server's full status page (every site's current requests and visitors) with SetHandler server-status or [H=server-status] | Critical | Three layers: sentora-guard.lua (mod_lua, after .htaccess and mod_rewrite) refuses with 403 a hosted site's handler for the panel's pool, another account's pool, server-status, server-info or proxying; in each hosted vhost, a Location block (merged after .htaccess, so a site can not undo it) gives PHP-FPM no script and none of the PHP settings for any socket but the account's own, and blanks status pages; and the panel's pool runs only the panel's own scripts (inc/fpm_guard.php as auto_prepend_file). The daemon puts all three in place on existing servers within 5 minutes; sentora-post-install-check and sentora-smoke-test check them |
| Protected Directories | A client could make the panel write into another account's files (a symbolic link put in place of a folder's .htaccess or of its password file, which the panel followed); the deletes did not check the owner, so one client could remove other clients' protections and users; passwords were hashed with old DES crypt salted from the password itself (deterministic, only 8 characters counted) and both usernames and passwords had to be unique across the whole server, so adding a user revealed whether anyone else used that password; the message and usernames were written unchecked (a line break added any Apache directive or password line); changing a password never worked (broken SQL); the password folder was made with 0777 | High | Rewritten: every record read and changed with the account's own id in the SQL; folders chosen in a tree of the account's own public_html and checked again on submit (real folders only, no links, nothing hidden or outside); files written as a new temporary file renamed into place, so a link is replaced, never followed; a marked block in .htaccess that is removed cleanly, leaving the folder's own lines as they were; bcrypt passwords; plain-character messages and usernames; the server-wide unique indexes dropped (the daemon does it on existing servers); the password folder 0750 and files 0640 |
| MySQL users | Every MySQL user's password was stored as plain text in the panel's database and shown on the MySQL Users page (Show Passwords) | High | The panel keeps no copy (MySQL stores its own hash): a new user's password is shown once when it is made; copies stored by older versions are removed by the daemon |
| MySQL users | Creating a MySQL user (or adding a database to one) took the database's id from the form without checking whose database it was: a client could give a user of their own full rights on another client's database (found by the cross-account test on 2026-11-05) | Critical | The database and the user must both belong to the account, checked inside the create and add actions, so the web service API is covered too |
| AutoIP | Given to every client (all three groups), with no administrator check: a client could point it at their own "what is my IP" address, which rewrote the server's IP and every customer's DNS records, and set a script the daemon ran as root. The settings were also saved by pasting the form's values into the SQL (injection) | Critical | Administrators only (the module refuses anyone else, fresh installs grant it to Administrators only, and the daemon removes the old client permissions on existing servers); the address must be http(s), the script a full path with no arguments, the email addresses valid, the SQL bound. The daemon runs the script only if it is a plain file owned by root that only root can change, in folders only root can change, and passes it the new and old IP |
| zsudo (panel -> root helper) | zsudo lets the panel user ask root to reload a few services. It checked the arguments against a strict whitelist, but never cleared the caller's environment. The loader strips LD_PRELOAD from a set-uid program, but not PATH, BASH_ENV or IFS, and the job runs through `at`, which replays the submitter's environment as root. `service` is a /bin/sh script that calls `systemctl` by its bare name, so anyone who could run zsudo (code running as the panel user, e.g. a panel RCE) could set PATH to a directory holding a fake `systemctl` and have it run as root - the whitelist did not matter, because the payload was in the environment, not the arguments (found and demonstrated on 2026-11-06) | Critical | zsudo now wipes the environment and sets a fixed safe PATH before it runs anything or submits the `at` job, and drops the inherited group. The whitelist, and running through `at` to escape the web server's sandbox, are unchanged A later review hardened the rest of the context too: a safe umask (`at` also replays the caller's umask, and a permissive one reached the root job), a fixed working directory, and inherited file descriptors closed. |
| Account restore (sentora-restore) | An account restore ran as root. Two problems: (1) each database dump was loaded with the panel's MySQL login, which is the MySQL root account (FILE, SUPER, CREATE USER, WITH GRANT OPTION); and an account's backup zips live in the account's own folder, so a client could edit a dump in their own backup to add `CREATE USER ... GRANT ALL ... WITH GRANT OPTION`, and an admin restoring that account would make the client a MySQL superuser (read and change every tenant's data). (2) the web files were copied in as root, so a symlink the account placed in its own folder could redirect a write outside it. Found 2026-11-06 | Critical | Each dump is now loaded by a temporary MySQL user granted only on that one database (so `CREATE USER`, `GRANT`, `FILE`/`OUTFILE` and cross-database statements are refused), read with `--defaults-file` so a stray `~/.my.cnf` can not put the panel login back, with `DEFINER` clauses stripped, and the user dropped afterwards. The web files are copied as the account's own user, as the full restore already did |
| Windows code | hMailServer and FileZilla code (11 files) for Windows servers: never used here, and another, unmaintained way of writing passwords | Low | Removed (the settings that choose the mail and FTP code are locked to Postfix and ProFTPD) |
| FTP accounts | FTP passwords were stored as plain text in the panel's and ProFTPD's databases, and the FTP page could show them all (Show Passwords) | High | Stored as SHA-512 crypt hashes only (salted, 50,000 rounds); ProFTPD accepts hashes only (`SQLAuthTypes Crypt`); existing passwords hashed by the daemon, so logins keep working; no passwords on the FTP page |

**SOGo**

- Users log in with their mailbox address and password from the panel, through a read-only view of the mailboxes.
- 21 settings in Admin > Mail Config (ActiveSync on or off, language, time zone, message size, filters, out-of-office, forwarding, reminders, login blocking, workers, ActiveSync intervals, nightly backup). The root daemon checks each value, writes them to `sogo.conf` and restarts SOGo.
- The Webmail page shows a "Launch Groupware" button and the phone setup details.

**Webalizer and Visitor Stats**

- Both are add-on packages now, no longer part of the core panel: install them from Repo Browser (repository `https://raw.githubusercontent.com/RusTus/sentora-installers-2027/master2027/sentora-repo`, listed by default; packages `webalizer_stats` and `visitor_stats`) or upload the `.zpp` in Module Admin. The package builds its program from the bundled source (Webalizer uses Ubuntu's package where there is one), makes sure the `sentora-stats` user exists and gives every user group the module. Removing it keeps the program and the reports, so a reinstall carries on. Servers that already have them keep them.

- Domains with no traffic yet are skipped instead of reporting failures.
- Webalizer, Visitors and GoAccess run as their own user, `sentora-stats`, which can read nothing else; the root job opens the logs and passes them in.
- Existing Webalizer reports move automatically from the old public folder on the next hourly run, keeping their history.

**Matomo**

- Set up unattended by the installer through Matomo's own installer steps; super user `sentora_admin`.
- Every 5 minutes the daemon creates a Matomo site per domain and subdomain (plus the panel domain for zadmin) and a view-only Matomo user per account, through a small Sentora plugin (`sentora:sync`).
- Every hour it imports only the new lines of each domain's access log (rotated logs restart from the top) and builds the reports. The import token is never on a command line.
- The panel page lists the account's own domains and opens the full Matomo interface with no second login. Each domain can switch to tracking code, with the snippet shown.
- Matomo's internet features, adverts and "what's new" pop-ups are switched off, and reports are built by the hourly job rather than by visitors.

## PHP 8.5 compatibility and bug fixes

The whole core now lints clean on PHP 8.5, and every panel page loads with no PHP warnings or errors as an administrator and as a client.

**PHP 8.5 compatibility**

- Template loops, module lists and controllers updated for PHP 8's stricter types and removed functions.
- Undefined variables, `count()` on null, array access on false and wrong static declarations fixed across Domains, DNS, MySQL, Services, Packages, Module Admin, Manage Clients, Backups and Domain Logs.

**Bug fixes**

- Apache: the port 80 to 443 redirect no longer catches `/server-status`, so Apache Status works on HTTPS panels; port 80 always listened on; a wrong port variable fixed.
- Services page: wrong port variable removed; DNS, SMTP, submission, IMAP(S) and POP3(S) checks added.
- AutoIP: tries several address services and validates the result.
- BIND: options removed in BIND 9.16+ dropped; its AppArmor profile disabled so zone files can be written; config checked before start.
- Sencrypt: a crash in the daily renewal fixed; the panel certificate is synced to mail and FTP within 5 minutes.

Postfix hands every message to clamav-milter and spamass-milter while the sender is connected: infected mail is refused (or held, or dropped), very high spam scores are refused, other spam is marked (X-Spam headers, a subject tag) and filed by a per-mailbox Sieve script that runs before the user's own filters (the Spam folder, or the inbox; optionally deleting scores of 15 or more). If a scanner is down, mail is still accepted. ClamAV is left off on servers with less than 2 GB of memory.
  - Admin > Server Admin > SpamAV Admin: status (each scanner's services, signature versions and dates, rules date, what Postfix scans with), Update virus signatures now, Update spam rules now, Restart the scanners, server-wide totals and the most common viruses, and two settings tables in the style of Sentora Config. ClamAV: on/off, what happens to infected mail, what happens when ClamAV is not working, scanning outgoing mail, the scanned header, size and archive limits, archives, PDF, Office, macros, HTML, phishing signatures and links, heuristics, password-protected archives, update frequency, threads. SpamAssassin: on/off, the spam score, the reject score, the subject tag, the report style, checking users' own mail, size limit, processes, network tests, Bayes learning and its thresholds, trusted networks, server-wide allowed and blocked senders, daily rule updates, whether users may change their settings, where spam goes by default, how long activity is kept. Every value is checked (type, range, pattern) before it is saved; the daemon writes the configuration files and restarts only what changed.
  - Mail > SpamAV, for every account: 7-day totals (checked, spam, viruses, refused), each mailbox's settings (spam filter on or off, sensitivity from strict to only obvious spam, the Spam folder or the inbox, deleting very high scores, allowed and blocked senders), and the recent activity (when, mailbox, sender, score and rules or virus name and subject, what happened), filtered by mailbox and type. Only the account's own mailboxes and domains are shown and changed; virus scanning can not be switched off by users; the administrator can make the settings read-only.
  - spamd reads per-mailbox settings from its own database (sentora_spamav, a read-only MySQL user); the activity comes from the systemd journal (Postfix, spamd, clamav-milter), read every 5 minutes.
  - The activity in Mail > SpamAV is shown 25 at a time (Newer, Older, Newest, Oldest, with the number of entries and pages) in a window of its own height whose column headings stay in view; the filters are kept from page to page.
  - Dashboard widget "Spam and viruses" (off by default; add it, or make it a default in Widget Admin): for administrators the scanners' status, the signatures, today's and the last 7 days' totals for the whole server and its latest 5 events; for everyone else the totals and latest 5 events of their own mailboxes.
  - sentora-post-install-check checks the scanners that are switched on and what Postfix scans with; sentora-smoke-test has two new steps: a virus (EICAR) and obvious spam (GTUBE) are refused.
- GoAccess and Matomo show their full page: the frame each is shown in grows and shrinks to the height of what is inside it (etc/lib/sentora/frame-height.js), so the panel page scrolls as a whole instead of the frame having its own scroll bar, and it keeps fitting as the content changes (Matomo loading reports, links inside the frame). GoAccess reports stay sandboxed: the report tells the panel its height (a number only, accepted only from that frame). Window-height minimums inside Matomo (its menu) are lifted so the page can be measured; a page that still grows with its frame is noticed and left at a fixed height.
- Status icons: the green check and red cross pictures (Module Admin, Service Status, Mailboxes, Forwarders, AutoIP, DNS Admin, DNS Manager, Repo Browser) are replaced everywhere by one set of icons drawn as inline SVG (dryden/ui/status.class.php, styled in both themes): a soft tinted circle with a check (good), a cross (bad) or an exclamation mark (warning), sharp at any size, each with a label for screen readers and a tooltip. The old picture files are removed (sentora-update removes them on existing servers). DNS Admin's General / Tools tabs work again: they used jQuery UI, which the panel does not load; they are now a few lines of plain JavaScript and remember the last tab.
- Widget Admin (Admin > Server Admin > Widget Admin): one row per dashboard widget, like Configure Modules: On/Off, Default (on new dashboards, and when an account goes back to the defaults), Order, and a tick box for each group that may use it (Server status stays administrators-only). "Apply the defaults to every account now" resets every arranged dashboard. Widgets can be uploaded as a .zip package with widget.xml (id, name, description, version, author, default, groups), widget.php (a class dashboard_widget_&lt;id&gt; with Render($user)) and an optional widget.css, described in etc/dashboard-widgets/README.md; an example package (Quick links) is included. Only administrators can upload. The panel checks the package and queues it; the daemon (root) checks it again (only those three file names, no folders, 1 MB at most, a safely read widget.xml, an id that is not a built-in widget, the class name, a PHP syntax check) and writes the files itself into etc/dashboard-widgets/&lt;id&gt;/, never unpacking paths from the zip. Only widget.css is served from there. A widget that fails shows "This widget could not be shown" without breaking the dashboard. Uploaded widgets can be removed, and a new version of one replaces the old and keeps its settings.
- Dashboard (Account Information > Dashboard): the page every login lands on (after the password, the two-factor code or a recovery code), with "Continue to your panel administration" to the panel's usual home page. Each account arranges its own widgets: add one from the list, remove it, move it up or down, or go back to the defaults. Widgets: Getting started (default: the steps to get a website running, from the domain and its DNS to mailboxes, a database and its user, FTP, uploading, HTTPS and backups, ticked off as they are done and linking only to modules the account may open), Account usage (default: disk, bandwidth, domains, subdomains, mailboxes, databases and FTP accounts against the package), Your domains, Security (two-factor login and recovery codes), Backups (latest backup and FTP backup), and Server status for administrators (disk, load, open alerts). Every group may open it; when it is switched off in Module Admin, logins go to the panel home as before.
- Two-factor recovery: when an account turns two-factor login on (or sets it up at a forced login) it gets 10 one-time recovery codes, shown once to print or save and stored hashed (bcrypt). At login each one can be used once instead of the app's code ("Use a recovery code" on the code page); the account then lands on My Account with how many are left. My Account shows the count and makes a new set (the old codes stop working) with a current code from the app. Manage Clients has a Reset two-factor button on each of the administrator's or reseller's own clients that use it, for a client who lost both phone and codes: two-factor login, its recovery codes and "Remember me" logins are removed (with enabled-forced the client sets it up again at the next login). Recovery-code logins and resets are logged in /var/lib/sentora/twofactor.log. A forgotten password is reset by email as before; two-factor login still applies after it.
- Two-factor login (Sentora Config) has three choices: disabled, enabled (each account turns it on in My Account, as before) and enabled-forced (every account must use it). With enabled-forced, an account that has not set it up gets a setup page right after its password (QR code, key, one code to confirm) and can not use the panel until it is done; a session opened before the switch, or a "Remember me" login, goes to that page too; My Account no longer offers Turn off. An administrator viewing a client's account is not interrupted. The old values convert by themselves (true: enabled, false: disabled). If an administrator loses their phone: setso --set twofactor_enabled disabled.
- Backup (Advanced > Backup): Back up now makes the backup on the page itself, in the background, instead of in a pop-up window. While it runs the page shows a progress panel (a spinner, when it started and how long it has taken, and that the client can leave the page) and asks for its progress every few seconds; when the backup is ready the page reloads with it at the top of the list. Every backup in the list has a Download button (before, a backup could only be downloaded from the pop-up right after it was made). A backup that stopped part way is reported, never shown as running for ever. The pop-up pages (launchbackup.php, dobackup.php) are removed.
- Clients' own FTP backups (Advanced > Backup > Copy my backups to my own FTP server): every day at the hour the client chooses, a new backup of their websites and databases (no mail) is uploaded to their FTP server, keeping the number of copies they choose. FTPS with TLS by default (implicit FTPS and plain FTP, with a warning, can be chosen; certificates are checked unless the client accepts a self-signed one); the password is stored encrypted and never shown again; Test connection and Upload now are run by the daemon within 5 minutes and the page shows the last test, upload and good copy. The server's address is checked after its name is looked up and then pinned: loopback and link-local addresses are always refused, private networks unless the administrator allows them, and on this server's own addresses only the FTP ports; the FTP server can not send the data connection elsewhere; the password reaches curl in a root-only file, never on a command line; at most two uploads run at once. Admin > Backup Config: "Client FTP backups" (on) and "Client FTP private networks" (off).
- Off-server backup (Admin > Backup Config > Off-server backup): every night copies this server's backups to another machine over SSH, or to a local folder such as an NFS mount: every account's backups, the panel backups, a dump of all MySQL databases made at that moment (the panel's own included), the configuration and, if ticked, the mailboxes. All settings are on the page: enabled, server, port, username, password (stored encrypted with the panel's key, never shown again; without one the SSH key from `sentora-offsite-backup --setup` is used), folder, time, nights kept and mailboxes, each checked on save. Test connection and Back up now are run by the daemon within 5 minutes, and the page shows the last test, the last good copy and the last error. The daemon keeps the nightly job in step with the time and the switch. Each night is a dated snapshot in which unchanged files are hard links to the night before, so only changes are sent and stored. The server alerts email when it is switched on and has not succeeded for 26 hours; `sentora-post-install-check` reports it too.
- `sentora-smoke-test` (run as root, about 2 minutes): uses the server the way a client does. It makes a temporary client with a domain, FTP account, mailbox, database and MySQL user through the panel's own pages, then uploads a page by FTPS, loads it (and checks PHP runs as the account's user), sends mail over SMTP and reads it over IMAP, logs in to SOGo and MySQL, checks Show password, backs up and restores the account, checks isolation and removes everything again. One line per step with PASS, FAIL or SKIP and a one-line reason (a step that needs a failed one is skipped and names it), then `RESULT: PASSED` or `RESULT: FAILED` with the failed steps listed again; exit code 0 only when everything passed; report in `/var/sentora/logs/smoke-test.log`; `--keep` leaves the test client in place.
- GoAccess: the reports are chosen from one drop-down (grouped by account for administrators, each with the time it was last updated) instead of a list with a row per domain, so the report stays in view with hundreds of domains; it opens on choosing, and shows the all-domains report (administrators) or the first domain by default.
- `sentora-update` (run as root): updates the panel in place from the GitHub release of sentora-core-2027 tagged `current`, and knows a new version by its changed SHA-256 (`TAG=` in `/etc/sentora/update.conf` picks another release, `TAG=latest` the newest; `URL=` uses your own web server). It checks the zip against the SHA-256 GitHub lists for it (`--check` answers from that without downloading; without GitHub's API it finds the newest release in the release feed), backs the panel up first (the last 5 backups are kept in `/var/sentora/backups`), copies the new core over the old without touching this server's own files (`cnf/`, `zsudo`, the template cache, Matomo's config, the repository lists, installed add-on modules), removes files the core no longer has (`bin/obsolete-files.txt`), sets the installer's permissions, registers new core modules, updates the Matomo and Roundcube databases when their versions change, runs the daemon once and then `sentora-post-install-check`. `--check` says whether an update is available, `--rollback` restores a backup.
- `sentora-restore <account> <backup.zip>` (run as root): restores an account from one of its backups (web files, databases or both). A backup of the current state is made first, only files under `public_html/` and dumps of the account's own databases are accepted from the zip, and restored files belong to the account's own user. Backups made by the daemon now belong to the account's own user too, so its FTP login can download them (they belonged to the web server user, which FTP no longer runs as).
- Automatic security updates: the installer installs and switches on Ubuntu's unattended-upgrades (security updates only, daily, no automatic reboot, old kernels removed); `sentora-post-install-check` checks it is on and has run.
- Server alerts: every daemon run checks disk space, the core services and the outgoing mail queue (over 100 messages often means a site sending spam) and emails the administrator when a problem starts, every 24 hours while it lasts and when it is resolved. Admin > Sentora Config: "Alert email address" (empty: the administrator account's address) and "Alert disk use percent" (85). Every alert is also written to `/var/sentora/logs/alerts.log`.
- Admin > Sentora Config "Confirm panel password to show passwords" (off by default) makes Show password (MySQL Users, FTP) ask for the panel password first. Mailbox passwords are never shown: a mailbox belongs to whoever uses it, so the account owner (or reseller) can only set a new one, and mailbox users change their own in webmail (Settings > Password, which changes that mailbox only, not any panel login).
- Show password (MySQL Users and FTP): each user and FTP account has a Show password button that shows its owner the password again. The panel keeps it encrypted (libsodium authenticated encryption, with a key derived from this server's secret in `cnf/security.php`), never as plain text, so a copy of the database alone holds only ciphertext; a password is only shown when its owner clicks (never in the page otherwise), only for the account's own users, and each view is logged in `/var/lib/sentora/password-reveal.log`. FTP logins are still checked against SHA-512 crypt hashes. Passwords stored as plain text by older versions are encrypted by the daemon (so they can still be shown); the MySQL password column is widened for the encrypted form (it was 40 characters).
- Matomo log import: the importer connects to Matomo on this server (127.0.0.1) under the panel's name, so it no longer fails when the server itself can not resolve that name in DNS ("Temporary failure in name resolution": no visits were recorded at all). Each hourly run now writes its result per domain to `/var/sentora/logs/matomo-import.log` (lines read, visits recorded, lines left out such as bots and static files, failures, domains using the tracking code), which the 5-minute daemon log used to overwrite.
- `sentora-post-install-check` (run by hand as root, read-only): checks the installation and prints OK, WARN or FAIL for each item: services running and started at boot, the fail2ban jails, MySQL, memcached and SOGo listening on this server only, permissions of the files holding passwords, each hosting account's own user, PHP pool and closed folder (and that one account can not read another's), no plain-text or MD5 passwords stored, the TLS settings, and that the daemon's last run was recent, complete and free of PHP warnings. Exit code 0 when nothing failed; the report is saved in `/var/sentora/logs/post-install-check.log`.
- Installer: both check scripts stay executable after the permission lockdown (the update check would otherwise have lost its execute bit), and 16 bundled Bootstrap files no longer carry world-writable permissions in the core zip.
- `sentora-update-check` (run by hand as root): lists which bundled apps (phpMyAdmin, Roundcube, Matomo, Tiny File Manager, GoAccess, and Adminer if installed) are behind their latest release on GitHub, including newer commits for apps bundled from a commit, and how many Ubuntu updates (and security updates) are waiting. It reads GitHub's public release pages (no API, no key), runs only when started and saves its report in `/var/sentora/logs/update-check.log` (System Log Viewer).
- Manage Clients: when an email address is already in use, the message names the account using it (administrators: any account; resellers: only their own clients).
- Installer: the code for CentOS, Debian 12 and Ubuntu 24.04 that could no longer run is removed (2,053 to 1,852 lines; every removed line was checked to be unreachable on Ubuntu 26.04), the dead docs.sentora.org links are replaced, git is installed for the update check, and the final summary mentions the add-on repository and the update check.
- PHP versions: the domain and subdomain lists mark a PHP version that gets no security fixes any more (red) or stops getting them within 90 days; the daemon's daily run lists the domains concerned; new installs no longer get PHP 8.1 (no security fixes since 2025-12-31), servers that have it keep it.
- GoAccess uses the Webalizer icon in the menu.
- The 3D pie charts on the usage pages no longer log "Undefined variable $MyData" (an argument left over from the older pChart).
- The database setup no longer gives groups access to two modules that no longer exist.
- Daemon log: Repo Browser reports each queued command (who queued it, how long it waited, how long it took, its result or why it failed), a total, and the number of repositories, available packages and recent failures; SOGo settings says when nothing changed; account file ownership reports the accounts checked and the files fixed (also in the 5-minute pass); FTP password hashes reports the number of FTP accounts.
- Repo Browser repositories: a new repository is listed straight away as QUEUED until the daemon has added it; one the daemon could not add is listed as FAILED with Retry and Remove; one that can not be reached shows FAILED (it showed NO) with a Retry button next to Remove; one change at a time per repository. Queued messages in Repo Browser and Module Admin say that the change can take up to 5 minutes (Repo Browser used to say "updated successfully" before anything had happened).
- Modules: a package's module.xml without a type tag no longer causes PHP warnings, and only the three real module types are accepted (the old check let any value through).
- Repo Browser and Module Admin: while a module's install, removal or upgrade waits for the daemon, its button shows a disabled "Queued", and a second job for the same module is refused (also from an old tab, a resent form or a second Module Admin upload, which used to overwrite the waiting package).
- PHP Versions: the running or stopped column checks each version's service again (it looked for the shared socket that per-account pools replaced, so every version showed "stopped").
- Matomo: its "Urgent PHP security update" warning is skipped when Ubuntu's patched PHP build is installed (Ubuntu fixes PHP without changing its version number); see `etc/apps/matomo/SENTORA-PATCHES.txt`.
