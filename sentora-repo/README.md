# Sentora-2027 add-on modules

Optional modules for Sentora-2027, installed from the panel's **Repo Browser**. New installs list this repository already.

| Module | What it does |
| --- | --- |
| `PHP-Adminer` | Adminer 6.3.0 for each account's own MySQL databases, locked to the panel login and the account's own MySQL users, in the panel's Light or Dark |
| `webalizer_stats` | Webalizer traffic reports for each account's domains, updated every hour, in the panel's Light or Dark (builds the webalizer program on install) |
| `visitor_stats` | Visitors reports for each account's domains: visitors per day, pages, referrers, search terms and browsers, in the panel's Light or Dark (builds the visitors program on install) |
| `log_forwarder` | Sends an account's website logs (and an administrator's server logs) live to its own log server: ELK, OpenSearch, Grafana Loki or Graylog, as syslog over TLS through the server's rsyslog. Clients' forwarding counts towards their package's bandwidth. Every supported system (202): rsyslog installed with the system's own packages, SELinux port labels where needed |
| `quickfig` | WordPress settings without editing wp-config.php (site address, debugging, security, memory, revisions, updates, scheduled tasks from the server), with rescue tools (a site stuck in maintenance, a plugin that breaks the site, the cache, new secret keys, the database connection, the debug log), earlier versions with one-click undo, and a Magento shop's cache, maintenance mode and its own tools (cache:flush, reindex, deploy mode) run in the background as the account's own user; a switch to https (addresses and the links in the database, with WP-CLI) and hourly reminders (debug mode left on, a stuck maintenance notice), a Magento shop's search terms kept small (bots' junk searches deleted weekly), a crawler blocker for every website (bad bots, scrapers posing as an old Chrome, robots.txt rules for the app it finds: WordPress, WooCommerce, Magento, OpenCart, PrestaShop, Joomla, Drupal and more), websites sharing the same files pointed out, who visited each website in the last 24 hours (with Block), hardening switches (no PHP in upload folders, xmlrpc.php off, security headers, always https, HSTS, one www address), a permissions check with Fix, and WordPress's updates at a glance. Files are read and changed by a worker confined to the account's own folder |
| `apps` | One-click WordPress, OpenCart and Snipe-IT for each account: pick a website (or a folder of it), a title and an admin; the panel makes the app's database and MySQL user (counted in the package, shown in MySQL Databases), and the daemon installs it as the account's own Linux user from a checked package (wordpress.org's SHA-1 and per-file checksums; OpenCart's release pinned by SHA-256; Snipe-IT's source pinned by commit, its libraries installed with Composer once per server as an unprivileged user), with no setup page left open. **Deploy from Git**: an app of the account's own from a Git repository (https, or SSH with a deploy key the panel makes for a private one), its branch, its web folder found (public, web, dist, build) or given, Composer's libraries, a database with its settings put in .env, Laravel's key, migrations and storage link; Deploy now, Roll back, a webhook that deploys on push, and a failed deploy goes back to where it was (with a notice). An app's code (Snipe-IT's too) is kept in the website's own _app folder, where the website's PHP may read it, and only its web folder is served. OpenCart is made safe as it asks (install folder removed, storage moved out of the website, admin folder renamed). Admin passwords are kept only as the app's own hash; the account's apps are listed with their addresses, versions and a Remove button (files and database) |
| `payment_plans` | Billing for administrators and resellers: prices for their packages (monthly, yearly), plans for their clients, numbered invoices with their details and a tax line, made ahead of each period with reminders; new clients on a priced package are billed by themselves (existing ones with one button); clients pay with the processor the seller chooses, PayPal or Stripe, into the seller's own account (or the seller marks an invoice paid). A payment counts only when the processor confirms it to the panel for exactly the invoice's amount. An invoice unpaid past the seller's grace days switches the client off; paying switches it on again. The seller sees its figures at a glance (received this month and this year, what its plans bring in a month, what is waiting), and every invoice keeps its history (every payment, refusal and change). Refunds and chargebacks made at PayPal or Stripe after a payment are found once a day (for 180 days, and while a chargeback is open), shown on the invoice and told to the seller, who decides what follows |
| `php_hardening` | **Web Hardening** (was PHP Hardening), administrators only: two guards for the websites, each off, watch only (nothing blocked; what would be is listed) or on. **ModSecurity** in Apache (installed switched off by every installer) with Sentora's copy of the OWASP Core Rule Set (CRS 4 LTS, in the core): how strict (level 1-3), the score at which a request is stopped, domains and rule numbers left alone; the panel itself is only watched, never blocked. **Snuffleupagus** in each PHP (the successor of Suhosin): rules to choose (eight gentle ones on by default), accounts left alone. One list of what both caught (account, domain or file, rule numbers, address), which adds new lines by itself while the page is open, with search, filters, older pages, a Look now button, and a Statistics tab (charts by kind of attack, day, hour, source and site). The daemon does the work from the panel's settings (no system names in the add-on): it tests Apache or PHP with the new settings first, reloads, and puts the old ones back if they do not run |
| `docker_hosting` | **Docker Hosting**: apps in containers on separate servers ("nodes"), never on the panel's. An administrator adds a node in the module (Nodes and apps): on a fresh AlmaLinux, Rocky Linux or RHEL 10 server, as root, `sudo bash sentora2027-node` (`node/sentora2027-node-alma10`) asks for the panel's address, shows the panel's code to check against the panel, installs rootless Podman, Caddy (automatic HTTPS) and the Sentora Node agent, and ends with the node's key, which the administrator pastes in "Add a node". The agent which calls the panel (nothing on the node is opened for it; every message signed and sealed with the panel's and the node's own keys, a one-time code links it). Shares pass down the account tree: the administrator gives resellers containers, CPU, memory, disk and apps, resellers give their clients part of theirs. A customer starts an app from the catalog (Uptime Kuma, Gitea, Vaultwarden, Nextcloud, and any image the administrator adds under Your own apps) at a name under one of its own domains, the A record added the way DNS Manager does if it asks; on the node it runs under the customer's own Linux user with its limits held by the kernel, on 127.0.0.1 only behind Caddy, and behind a setup password until its owner opens it to the public. Each app's row says in words how it is (running, open to everyone or password protected, a newer version out) and has two switches, Nightly updates and Open to everyone, then Update, Stop/Start, Restart, Logs, Settings (size, and under Advanced the app's own settings, which its owner may change: the app restarts with them and goes back to the old ones if it does not start) and delete; an update goes back to the old version when the new one does not start; switched-off accounts' containers stop, deleted accounts' go, a container over its disk limit stops. From the panel, for each node: update it, its system's security updates (also by themselves at night), restart, certificate settings; warnings on the page and by email. The apps can not reach the local network (private addresses) unless an administrator opens it for that customer (Nodes and apps > Local network). Tests: `tests/docker_hosting/run.sh` (stand-in panel, real agent, fake Podman) and Actions > Node test (real AlmaLinux and Rocky Linux 10 nodes) |

## Using it

On a server installed before this repository moved here, add it once in **Admin > Repo Browser**:

```text
https://raw.githubusercontent.com/RusTus/sentora-installers-2027/master2027/sentora-repo
```

Then refresh the list and install modules from it. Every download is checked against `SHA256SUMS`; a module that doesn't match isn't installed.

## Adding or updating a module

1. Put `<name>.zpp` (a zip of the module folder) in this folder. The file name, without `.zpp`, becomes the module's folder name: letters, numbers, `_` and `-` only.
2. Add `<name>` on its own line in `packages.txt` (new modules only).
3. For an update, raise the version to the same number in two places: `<version>` in the module's own `module.xml` (inside the `.zpp`) and `<latestversion>` in `<name>.xml` here. Servers with the module installed see the higher number within an hour: the administrators get a notice, and Repo Browser lists it under **Updates**.
4. A module sets up everything it needs itself, with no change to the panel: `deploy/install.run` runs as root when it is installed, and `deploy/upgrade.run` runs as root after each update, in the panel's folder. Put repairs of anything an earlier version set up wrongly (folders, permissions, settings) in `upgrade.run`, so an update fixes a server at once. Visitor Stats does this for its reports folder.
5. Update the checksums, then commit to `master2027`:

   ```bash
   sha256sum *.zpp > SHA256SUMS
   ```

GitHub can take a few minutes to serve a new commit at the address above.

> [!WARNING]
> Installing a module runs its code inside the panel. Only add modules you trust.
